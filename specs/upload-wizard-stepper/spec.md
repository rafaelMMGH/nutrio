# Spec: Upload wizard stepper

**Status:** implemented (v1.3.4; all stories built and T016 e2e gate passed 2026-11-18; approved by the user)
**Version:** 1.3.4 · **Branch:** feature/upload-wizard-stepper (from `alt-dashboard`) · **Owner:** Rafael Martinez

> Budget: ~150 lines. The *what* and *why* only; no technology choices (those go in plan.md).

## Overview

The PDF upload wizard ("Creación de Plan Nutricional") walks the user through 8 steps (Subir, Procesar, Datos, Comidas, Ingredientes, Complementos, Duplicados, Confirmar) shown in a horizontal stepper. Most steps are read-only or static text, and only name and objective are editable, so the flow feels long for little to do. There is also a bug: going back to the first step after a PDF has been uploaded shows the "Listo para confirmar" card instead of the upload step. This feature reduces the wizard to 4 clearer steps, presents them in a vertical stepper with direct navigation back to reached steps, and fixes the bug. In v1.3 the Subir step becomes a file dropzone that uploads as soon as a PDF is added, shows progress and failures on the file's own row, and has one control (the ✕) to remove the file and start over.

## Goals / Non-goals

- Goals: 4 steps with a stepper that shows progress and problems and allows jumping back; meals reviewed in one place; fix the step-1 fall-through bug; upload by drag and drop, picker or paste with visible progress and inline retry.
- Non-goals: changes to PDF parsing, the data model, the confirm payload or other modals. The upload API changes only by adding the 413 size check (REQ-26).

## Decisions

Labels (Spanish): Subir "Tu PDF del plan"; Datos "Nombre, objetivo y calorías"; Comidas "Opciones, ingredientes y complementos"; Confirmar "Revisa y activa el plan".
Terms: *rechazo* = a file refused before upload, or a server 413; *falla* = an upload or processing error, which can be retried.

- 4 steps: fewer, clearer; 3 would bury the editable name, 2 would make the stepper meaningless. Vertical 200px rail, compact at 937px and below: standard desktop pattern, follows the project breakpoint. Heading and `.upload-wizard-modal` kept (tests and styles depend on them); only the active step shows its description: keeps the rail clean.
- Comidas error is informational only and Comidas is the only step that can be in error: the user may knowingly accept an imperfect plan. Locking depends only on progress, never on error: a step with a problem must stay reachable to fix it.
- Steps up to the furthest reached stay selectable: jumping back must not lose progress. A reached step not yet passed reads "disponible"; the current step shows the current-step marker and no status text (except error): one clear "you are here" signal. The error marker shows as soon as processing finishes, even while locked: problems are visible early. After processing, Subir shows the file row and the "PDF procesado" card: fixes the fall-through bug.
- Subir is a file dropzone adapted from the uiarc File dropzone (MIT); the whole target is one button; drag and drop, picker and paste: better UX than a bare file input. Upload starts on add and "Procesar PDF" is removed: fewer steps.
- Two phases on the row, "Subiendo… N%" (✕ cancels) then "Procesando PDF…" (no ✕): shows what really happens; cancelling during processing would leave an orphan draft. A failure shows on the row with "Reintentar" and ✕: the error sits next to its file and retry is one click.
- Rules: PDF only, one file, at most 20 MB, checked in the browser and on the server (413): a plan PDF is small, and the server check stops huge files being loaded into memory.
- Server 413 (user decision 2026-11-17): same message and alert as the browser rejection but it also removes the row (REQ-22), mapped by status code so a proxy 413 with no body or an HTML body behaves the same, also during "Subiendo". Every other 4xx/5xx keeps the failed row. Retrying the same file cannot succeed, so "too large" gets one outcome.
- Cancel guarantee (user decision 2026-11-17): the ✕ disappears at 100%; before that, cancelling guarantees no draft and no stored copy, because the server stores the copy only after receiving the whole body. A click in the same instant the transfer completes may still create a draft: accepted, a cleanup would add work for a window of a few milliseconds. A PDF that fails to *process* still leaves its copy in `data/private-pdfs`, as today: out of scope.
- One ✕ means "remove and start over" in every phase ("Cambiar PDF" is removed): most minimal option. On a processed file it soft-deletes the draft without asking, recoverable from the Papelera, and discards Datos edits: the user is starting over. A failed deletion keeps the row and shows an inline error on it: the user is never told the draft is gone when it is not (constitution principle 6). Uploading archives the active plan and removing the draft does not restore it: existing behavior, out of scope; stated so nobody expects a restore.
- The wizard X does not delete the draft or ask: keeps today's behavior. It is disabled while a request runs: the user cannot abandon a request of unknown outcome. "Siguiente" is hidden until a PDF is processed: no advancing with nothing processed. "Confirmar plan" shows a visible busy indicator (drift fix: `aria-busy` alone is invisible).
- Focus goes to the step heading after "Siguiente"/"Anterior" but stays on the stepper after a jump: users keep their place. When a control disappears or is disabled, focus goes to the control that continues the task (REQ-16), or it would drop to the page. No "Todos los pasos completos" announcement: the wizard closing on success covers it.
- Collapsible meal cards, review-needed ones expanded and labelled (not color alone): long list stays scannable.
- Empty name blocks "Siguiente" and "Confirmar plan"; blank name on Confirmar shows "El nombre es obligatorio" (Gate 3): a nameless plan must not be confirmed, and the summary must not show a name the plan would not get.
- Scrolling content with fixed header and footer: actions are never pushed off screen at 390px. Accessibility floor in numbers (REQ-19): measurable instead of "legible". Datos unchanged, Confirmar a short summary: no scope growth. Branch from `alt-dashboard`: the current shell lives there.
- No toasts in the wizard (user decision 2026-11-17): new features do not use toasts, and feedback appears inline next to what it is about. Success shows through the processed row and card (upload) or the wizard closing (confirm); each failure shows inline and is announced once (REQ-4, 15, 24, 25).
- Announcements name the file ("Se agregó <nombre>", "PDF procesado: <nombre>") and sizes read "1.2 MB" (Q21): the user knows which file a message is about, in one familiar format. Fallback reasons ("sin conexión con el servidor", "error del servidor (<status>)") keep a failure from ever being blank or a raw body.
- One shared inline alert (user decision Q23, 2026-11-17; the uiarc Alert is only the design reference), persistent with no dismiss button: one consistent in-flow message pattern instead of toasts, and each alert closes on its own when its cause goes away. Rejections (REQ-22, the 413 of REQ-26) are danger alerts under the dropzone and the only interrupting ones; a failed draft removal (REQ-4) is a warning under the file row and a failed confirm (REQ-15) a warning above the footer, both announced politely once. A failed upload or processing (REQ-24) does not use the alert: the failed row is the message.
- Drag-over while a row is present keeps the normal prompt (Q21): "Suelta el PDF para subirlo" would promise an upload that REQ-22 rejects.
- Tests: unit tests for locking, caption plural, the REQ-22 check order and PDF rule, and the 20 MB server limit (a stream that errors if read past the limit) fail first; update `theme-palette.spec.ts`, the e2e helpers and every test that used the file input or "Procesar PDF"; add dropzone e2e tests (drag-drop, picker, paste, wrong type, empty file, over 20 MB, server 413, second file, progress, the two phases, cancel, retry, ✕ restart). E2e is written during the freeze, run and passing before merge.

## User stories

### US1 (P1): Four-step wizard with vertical stepper and navigation
As a user uploading a nutritionist PDF, I want a short wizard with a visible stepper I can navigate so that I can review and correct the plan quickly before confirming.

- **REQ-1:** The wizard has exactly 4 steps, in order: Subir, Datos, Comidas, Confirmar, each with the label and description listed in Decisions.
  - Given the wizard is open, when it renders, then the stepper lists 4 steps in that order and only the active step shows its description (on Comidas in error, the error text replaces it, REQ-10).
- **REQ-2:** At widths of 938px and above, the stepper is vertical in a left rail 200px wide with step content to its right. At 937px and below it is compact (markers plus one caption) and content spans the full modal width. The compact caption shows the error text from REQ-10 when the current step is in error, otherwise the current step name.
  - Given a 1280px viewport, then the stepper is a 200px vertical rail beside the content; given 390px on Datos, then only markers and the caption "Datos" show and content is full width.
  - Given a 390px viewport on Comidas with 2 options needing review, then the caption reads "2 opciones necesitan revisión".
- **REQ-3:** A step is completed once the user has passed it (moved on to a later step); "completed" is used only for the marker and screen-reader status, and never for the current step (REQ-6). A step that has been reached (up to the furthest reached) but not passed is "available" (REQ-6). Selectability depends only on progress: every step up to the furthest step reached, including the current one, can be selected with pointer or keyboard; steps beyond the furthest reached cannot and are skipped by keyboard focus order. Error state never affects selectability.
  - Given the user is on Confirmar, when they select Datos, then Datos is shown with edits preserved.
  - Given the user is on Datos (furthest reached), when they try to select Confirmar, then nothing happens and Confirmar is not focusable.
  - Given the user reached Confirmar and Comidas is in error, when they select Comidas, then it opens; after jumping back to Datos, Comidas and Confirmar remain selectable.
- **REQ-4 (v1.3):** After a PDF is processed, Subir shows the file row (✓, file name, size, and a ✕ with accessible name "Quitar <file name>" and tooltip "Quitar y empezar de nuevo") and below it the "PDF procesado" card with counts of meals, options, ingredients and complements and the review note shown today. There is no "Cambiar PDF" button. Selecting the ✕ soft-deletes the draft plan created by the upload (recoverable from the Papelera) without asking, discards unsaved Datos edits, resets progress, counts and the Comidas error state (recomputed after reprocessing), empties the dropzone and moves focus to it. If the deletion fails, a warning alert under the file row shows "No se pudo quitar el PDF. Inténtalo de nuevo.", announced politely once (REQ-25); the row and card stay and the alert closes on the next attempt.
  - Given a processed PDF, when the user returns to Subir (via "Anterior" or the stepper), then the row and card show and "Listo para confirmar" does not.
  - Given a processed PDF and Datos has an edited name, when the user selects the ✕, then the draft appears in the Papelera, the dropzone is empty and focused, Datos edits are gone without a prompt, and Datos, Comidas and Confirmar are locked until a new PDF is processed; a later PDF with different results shows only its own counts and Comidas error state.
  - Given the draft cannot be deleted, when the user selects the ✕, then "No se pudo quitar el PDF. Inténtalo de nuevo." shows under the row and is announced politely once, the row and card stay and focus returns to the ✕.
  - Given the user had an active plan before the upload, when the ✕ removes the draft, then that earlier plan stays archived and is not restored.
- **REQ-5 (v1.3):** The footer shows "Anterior" and "Siguiente"; "Anterior" is disabled on Subir. On Confirmar the primary action is "Confirmar plan". On Subir, "Siguiente" is hidden until a PDF has been processed (so also while uploading, processing or after a failure). "Confirmar plan" is disabled whenever the name is empty after trimming, until a name exists.
  - Given no PDF has been processed, when Subir shows, then there is no "Siguiente" and "Anterior" is disabled.
  - Given the user is on Confirmar, when they select "Confirmar plan", then the plan is confirmed with the same request content as today (trimmed name and objective edits plus confirmed status).
  - Given the user jumped back from Confirmar and cleared the name, when they return to Confirmar, then "Confirmar plan" is disabled; when a name is entered on Datos and they return, then it is enabled.
- **REQ-6:** The stepper is accessible: a labelled navigation ("Progreso") when interactive; the current step is identified as the current step (`aria-current`) and reads no status text unless it is in error; each other step exposes a Spanish screen-reader status (completada: passed; disponible: reached but not passed; sin iniciar: beyond the furthest reached); only Comidas can be "con error", which takes precedence over the others and applies even to a locked or current Comidas; the current step shows the current-step marker, never a check, even if it was already passed (for example Datos after jumping back); a polite announcement reads "Paso N de 4: <label>" on every step change; arrow keys, Home and End move focus among selectable steps and Enter or Space selects one.
  - Given keyboard focus on a selectable step, when the user presses Enter, then that step becomes active; on moving to step 3, "Paso 3 de 4: Comidas" is announced.
  - Given processing finished with options needing review and Comidas still locked, then a screen reader reads Comidas as "con error"; given the user reached Confirmar and jumped back to Datos, then Confirmar reads "disponible"; given a new upload with nothing reached beyond Subir, then it reads "sin iniciar".
  - Given the user passed Datos and then selects it again from Confirmar, then Datos is the current step, reads no status text and shows the current-step marker, not a check; once they move on, Datos reads "completada" with a check.
- **REQ-7:** Stepper animations (connector fill, current-step ring, number to check or alert transition, description reveal) are disabled when the user prefers reduced motion, and the stepper is legible in light and dark themes.
  - Given reduced motion is enabled, when the step changes, then the new state shows immediately with no animation.
- **REQ-14 (v1.3):** While a request runs, the wizard is locked: stepper steps, "Anterior", "Siguiente", the wizard X and form inputs are disabled. Requests are the upload ("Subiendo" and "Procesando PDF"), the draft deletion by the ✕ and "Confirmar plan". The control that triggered the request shows a visible busy indicator, not only an exposed busy state: the ✕ during deletion, "Confirmar plan" while confirming. On Subir, each control is in this state per phase:

  | Phase | Dropzone | Row ✕ | Reintentar | X | Anterior | Siguiente | Stepper |
  |---|---|---|---|---|---|---|---|
  | Empty | accepts a file | none | none | enabled | disabled | hidden | Subir only |
  | Uploading | rejects only | cancels | none | disabled | disabled | hidden | disabled |
  | Processing | rejects only | none | none | disabled | disabled | hidden | disabled |
  | Processed | rejects only | deletes draft | none | enabled | disabled | enabled | enabled (REQ-3) |
  | Deleting | rejects only | busy, disabled | none | disabled | disabled | disabled | disabled |
  | Failed | rejects only | removes file | enabled | enabled | disabled | hidden | Subir only |

  The dropzone is operable in every phase, but while a row is present it only produces the "Sube un solo PDF a la vez" rejection (REQ-22). After the ✕ is selected, a second click or a late completion does nothing.
  - Given "Confirmar plan" or the draft deletion is running, then its control (the ✕ for deletion) shows a visible busy indicator; when the user clicks it again, a stepper step, "Anterior" or the X, then nothing happens and no second request is sent; when it finishes, controls are enabled again.
  - Given "Subiendo… N%", then the row ✕ cancels and the X, "Anterior" and the stepper are disabled; given "Procesando PDF…", then the row has no ✕ and the X is disabled.
  - Given a failed row, then the X, dropzone, "Reintentar" and ✕ are enabled and "Anterior" is disabled.
- **REQ-15 (v1.3.2):** If "Confirmar plan" fails, a warning alert "No se pudo confirmar el plan: <motivo>" shows above the footer on Confirmar and is announced politely once (REQ-25); <motivo> follows the fallback rules of REQ-24. The wizard stays on Confirmar, all edits are kept, controls are enabled again and focus goes to "Confirmar plan" (REQ-16). The alert clears when "Confirmar plan" is pressed again (so a repeated failure is announced again) or when the user leaves the step. On success the wizard closes with no message and the page refreshes to show the plan as active.
  - Given confirmation fails, then the alert shows above the footer and is announced politely once, Confirmar is still active, the edited name is intact and focus is on "Confirmar plan"; when the user selects it again, or leaves the step and returns, the message is gone.
  - Given confirmation succeeds, then the wizard closes with no message and the page shows the plan as active.
- **REQ-16 (v1.3.4):** While a request runs, its triggering control (the ✕ during deletion, or "Confirmar plan") shows busy; when the request ends, focus goes to the outcome target below, and is never left on the page body. On step change by "Siguiente" or "Anterior", focus moves to the new step's heading. After a jump from the stepper, focus stays on the stepper. After a failed confirm, focus returns to "Confirmar plan"; after a failed draft deletion, to the ✕; after a failed upload or processing, to "Reintentar" (REQ-24). Focus moves to the dropzone after any row is removed (✕ on a processed, failed or uploading row, or a server 413), when "Reintentar" is selected, and when the cancel ✕ disappears at 100% while it has focus. After a successful upload and processing, the wizard stays on Subir (it does not advance) and focus moves to the "PDF procesado" heading. While the wizard is open, the page behind it cannot be reached: keyboard focus and screen readers stay inside the wizard (the top bar, sidebar, page content and the assistant are inert) and everything is reachable again when the wizard closes, because the wizard is a modal.
  - Given the wizard is open, when the user presses Tab repeatedly, then focus never leaves the wizard.
  - Given processing succeeds, then the wizard is still on Subir, the row and "PDF procesado" show and focus is on its heading, so the user can review it or select the ✕ before moving on.
  - Given the user is on Datos, when they select "Siguiente", then focus is on the Comidas heading; when they instead jump from the stepper, focus remains on the stepper.
  - Given confirmation fails, then focus is on "Confirmar plan"; given the upload fails, then on "Reintentar"; given a row is removed by its ✕ (cancel, failed or processed) or by a 413, or focus was on the cancel ✕ at 100%, or "Reintentar" is selected, then on the dropzone.
- **REQ-17 (v1.3):** Closing the wizard with the X closes it immediately, even with unsaved edits and without asking, except while a request is running (REQ-14). An uploaded draft plan is kept as a draft, and a failed row (no draft) needs no cleanup.
  - Given the user edited the name on Datos and no request is running, when they select the X, then the wizard closes with no prompt and the draft is not deleted; given an upload is running, then the X does nothing.
- **REQ-18 (v1.3.3):** The content area scrolls when taller than the modal, while header and footer stay visible, at widths down to 390px, with no horizontal scrolling. While the wizard is open it sits above every other floating control, including the assistant button, so nothing covers its footer.
  - Given the wizard is open at 390px, then the assistant button is not shown over it and the footer buttons are fully visible and selectable.
  - Given many meals with long names at 390px, when the user scrolls Comidas, then header and footer remain visible and there is no horizontal scroll.
- **REQ-19 (v1.3.3):** Text meets WCAG AA contrast (4.5:1) and non-text UI (markers, connectors, borders, progress bars, dropzone outline, focus ring, alert icon and edge) meets 3:1, in light and dark themes, including the dropzone text, drag-over state, failure message and alert text. Every focusable control inside the wizard shows a visible focus ring, which takes precedence over the app's shared focus style. In the compact layout, stepper markers, card headers, footer buttons, the dropzone, the row ✕ and "Reintentar" are at least 44px by 44px.
  - Given the compact layout, when measuring a marker, a card header, a footer button, the dropzone, a ✕ and "Reintentar", then each is at least 44px by 44px; given keyboard focus on any interactive element in either theme, then a focus ring of at least 3:1 contrast is visible.

### US2 (P2): Comidas review with collapsible cards
As a user, I want the detected meals in collapsible cards with problems highlighted so that I can find and check uncertain options fast.

- **REQ-8:** Comidas shows one card per detected meal. The header shows meal name, time window and option count. Expanded, it shows each option with its ingredients and confidence badge, plus the meal's complements (add-ons) and equivalents. A meal with no options still shows its card with "Sin opciones detectadas".
  - Given a plan with 4 meals, when Comidas opens, then 4 cards show with name, time window and option count; a meal with 0 options shows "Sin opciones detectadas" when expanded.
- **REQ-9:** Meals with at least one option that requires review start expanded and are highlighted with a visual treatment and a "Requiere revisión" label in the header; all others start collapsed.
  - Given one meal has an option needing review, when Comidas opens, then that card is expanded, highlighted and labelled, and the rest are collapsed with no label.
- **REQ-10:** Comidas is in error state when no meals were detected or at least one option requires review. The error marker shows as soon as processing finishes, even while Comidas is still locked. The error caption reads "No se detectaron comidas en el PDF" when no meals were detected, otherwise "1 opción necesita revisión" or "N opciones necesitan revisión" (N > 1). In the vertical rail the caption shows under Comidas, and when Comidas is the current step and in error the error text replaces its description, so only one line shows (the error is the more useful information); in the compact layout it shows as the caption only while Comidas is the current step (REQ-2), and otherwise the marker and its screen-reader status (REQ-6) carry the error. The error state never blocks navigation or confirmation. Comidas is the only step that can be in error: Subir, Datos and Confirmar never show the error status (marker, caption or screen-reader text).
  - Given 2 options require review, when the stepper renders at 1280px, then Comidas shows the error marker and "2 opciones necesitan revisión"; given exactly 1, then "1 opción necesita revisión"; given no meals were detected, then "No se detectaron comidas en el PDF" with the error marker.
  - Given processing just finished with 2 options needing review and the user is on Subir, then Comidas shows the error marker while still locked.
  - Given Comidas is in error, when the user selects "Siguiente" and then "Confirmar plan", then both work; given meals were detected and no option requires review, then Comidas has no error state.
  - Given any plan, including one with problems, then Subir, Datos and Confirmar never show the error status, whether current, locked or reached.
  - Given Comidas is the current step and in error at 1280px, then under Comidas only the error text shows and its description does not.
- **REQ-11:** Datos shows editable name and objective inputs plus kcal and macros, as today. If the name is empty after trimming, an inline message "El nombre es obligatorio" shows and "Siguiente" is blocked on Datos.
  - Given the name is cleared, then "El nombre es obligatorio" shows and "Siguiente" cannot advance; given an edited name, then Confirmar shows it.
- **REQ-20:** Each meal card header is a button that exposes its expanded or collapsed state to assistive technology; Enter and Space toggle it, and it shows a visible focus ring.
  - Given keyboard focus on a card header, when the user presses Enter or Space, then the card toggles and its exposed state changes.

### US3 (P3): Confirmar summary
As a user, I want a short summary before activating the plan so that I can confirm with confidence.

- **REQ-12:** Confirmar shows plan name (the edited name when one exists, otherwise the detected name; if the user cleared it, the Plan row shows "El nombre es obligatorio" in the warning style used on Datos, never the detected name, and "Confirmar plan" stays disabled per REQ-5), kcal, number of meals and options, supplements, and recommendations (collapsed by default). If the plan has no supplements or no recommendations, that block is omitted entirely.
  - Given a processed plan, when Confirmar opens, then those items show and recommendations are collapsed; given no supplements, then no supplements block or empty note shows.
  - Given the user cleared the name on Datos, when Confirmar opens, then the Plan row shows "El nombre es obligatorio" in the warning style, not the detected name, and "Confirmar plan" is disabled.
- **REQ-13:** Confirmar shows the note: "Las recetas con los mismos ingredientes, cantidades y unidades se reutilizan en lugar de duplicarse."
  - Given Confirmar is open, then the note shows verbatim.

### US4 (P1, v1.3): File dropzone upload
As a user, I want to drop, pick or paste my PDF and see it upload so that I can start without extra steps and see what is happening or what went wrong.

Scope: REQ-21 to REQ-26 plus the v1.3 changes to REQ-4 (row, ✕, no "Cambiar PDF"), REQ-5 ("Siguiente" hidden), REQ-14 (control states), REQ-16 (focus), REQ-17 (X and failed rows) and REQ-19 (dropzone, ✕ and "Reintentar" targets, contrast).

- **REQ-21:** Subir shows the heading "Sube tu PDF" and one dropzone target with the prompt "Arrastra tu PDF aquí", the secondary line "o elígelo desde tu equipo" and the note "Solo PDF · máximo 20 MB". There is no intro paragraph and no "Procesar PDF" button. The whole target is a single button: Enter or Space opens the native file picker. Adding a valid PDF by drop, pick, or paste (⌘V/Ctrl+V while the pointer or focus is on the dropzone; on touch devices, while focus is on it) starts the upload immediately. While a file is dragged over an empty dropzone, the prompt reads "Suelta el PDF para subirlo"; while a row is present the prompt stays normal, because that drop is rejected (REQ-22).
  - Given an empty dropzone, when a file is dragged over it, then the prompt reads "Suelta el PDF para subirlo" (and returns to normal when it leaves); given a row is present, when a file is dragged over, then the prompt stays "Arrastra tu PDF aquí"; when the user drops a valid PDF, then a file row appears and "Subiendo… N%" starts with no other action.
  - Given focus on the dropzone, when the user presses Enter or Space and chooses a valid PDF, then the upload starts; given the picker is closed without a choice, or the clipboard holds only text on ⌘V or Ctrl+V, then nothing happens; given a PDF in the clipboard and the pointer over or focus on the dropzone, then ⌘V or Ctrl+V starts the upload.
- **REQ-22:** The dropzone accepts only one PDF of at most 20 MB. A file is a PDF if its type is `application/pdf` or its name ends in `.pdf` (any letter case). Checks run in this order and a failing file never uploads: more than one file, or a file added while one is present, gives "Sube un solo PDF a la vez"; a file that is not a PDF gives "Solo se aceptan archivos PDF"; a 0-byte file gives "El PDF está vacío"; a file over 20 MB gives "El PDF pesa más de 20 MB". The message shows under the dropzone as a danger alert, one at a time (a new rejection replaces it, also while a row is present), with no dismiss button, and closes when the next file is added, the ✕ is selected, "Reintentar" is selected or the wizard closes. If the same rejection happens again while its alert is open (for example two images dropped one after the other), the alert closes briefly and reopens, so the message is announced and shown again (Q24). After a browser-side rejection the current file and its state are unchanged; a server 413 (REQ-26) instead removes the row and moves focus to the dropzone.
  - Given the user drops 2 files, or drops a PDF while a row is present, then "Sube un solo PDF a la vez" shows and no request is sent.
  - Given an image, or a file named `PLAN.PDF` with no type, is dropped, then the image gives "Solo se aceptan archivos PDF" and the other is accepted; given a 0-byte PDF, then "El PDF está vacío"; given a PDF over 20 MB, then "El PDF pesa más de 20 MB"; in every rejection no request is sent.
  - Given a rejection message shows, when the next file is added, the ✕ or "Reintentar" is selected, or the wizard closes, then the message is gone; given "Solo se aceptan archivos PDF" is open and a second image is dropped, then the alert closes briefly, reopens and the message is announced again.
- **REQ-23:** The file row has two phases. While uploading it shows "Subiendo… N%" with a determinate progress bar (exposed to assistive technology as a progress bar with its value) and a ✕ with accessible name "Cancelar subida de <file name>" that cancels: the transfer is aborted, the row is removed and the dropzone is empty and focused. When the transfer reaches 100%, the ✕ disappears and the row shows "Procesando PDF…" with an indeterminate animated bar. When processing succeeds, the row becomes the processed row of REQ-4. In every phase the file name is truncated to one line with an ellipsis, the full name stays in the accessible name and the tooltip, the size reads with a unit following the reference rules (for example "1.2 MB"; a whole number at exactly 1 MiB and at 10 MB and above), and the size and ✕ stay visible at 390px with no horizontal scroll. The server creates the plan and stores the PDF copy only after receiving the whole body.
  - Given a large PDF uploading below 100%, when the user selects the ✕, then the transfer is aborted, no draft exists in the Papelera, no copy of the PDF is stored, the row is gone and the dropzone is focused.
  - Given the ✕ was selected, when it is selected again or the transfer completes late, then nothing happens and no row reappears; given the click lands in the same instant the transfer completes, then a draft may still be created (accepted edge case, not tested).
  - Given the transfer reached 100%, then the row reads "Procesando PDF…" with an indeterminate bar and no ✕; if processing then fails, the stored copy remains as today (out of scope).
  - Given a file name of 120 characters at 390px, then the name shows on one line ending in an ellipsis, its full name is in the accessible name and tooltip, and the size and ✕ are visible with no horizontal scroll.
- **REQ-24:** If the upload or processing fails (any 4xx/5xx other than 413, or an upload that ends with no HTTP response: a network error or a connection closed by the server or a proxy), the row shows "No se pudo procesar el PDF: <motivo>" with "Reintentar" and a ✕, and focus moves to "Reintentar". <motivo> is the readable message in the error body; with no response it is "sin conexión con el servidor", and when the error body has no readable message it is "error del servidor (<status>)", for example "error del servidor (500)". The failure message is the single polite status announcement (REQ-25) and is not also an alert. "Reintentar" sends the same file again from the start, the row returns to "Subiendo… N%" and focus moves to the dropzone (REQ-16). The ✕ has accessible name "Quitar <file name>", only removes the file (no draft exists, nothing is deleted), empties the dropzone and moves focus to it. Accepted caveat: if the server answers 413 early and closes the connection, some browsers report a network error instead, so the user sees a failed row; this only happens when the browser-side 20 MB check was bypassed. The wizard stays on Subir with later steps locked and controls enabled (REQ-14).
  - Given the connection drops with no response, then the row shows "No se pudo procesar el PDF: sin conexión con el servidor", "Reintentar" is focused and the message is announced once, politely; given a 500 with no readable message, then it reads "...: error del servidor (500)"; when "Reintentar" succeeds, the processed row shows; when the user selects the ✕ instead, the dropzone is empty and focused and the Papelera is unchanged.
- **REQ-25 (v1.3.2):** The dropzone is operable and perceivable without sight or pointer, with motion options: a file addition is announced as "Se agregó <nombre>" and completion as "PDF procesado: <nombre>"; progress is a progress bar; each failure (upload or processing, draft removal, plan confirmation) is announced once politely; rejections (REQ-22 and the 413 of REQ-26) are the only interrupting alerts; with reduced motion enabled the indeterminate bar, drag-over transitions and the appearance and disappearance of an inline alert do not animate; it is legible in light and dark themes.
  - Given a screen reader, when a PDF is added, then "Se agregó plan.pdf" is announced; when processing completes, "PDF procesado: plan.pdf" is announced, and when processing, draft removal or confirmation fails, a polite announcement reads the failure message once; when a file is rejected, an alert reads the message; given reduced motion, then "Procesando PDF…" shows with a static bar and its text still conveys the state.
- **REQ-26:** The upload endpoint enforces the 20 MB limit (20 × 1024 × 1024 bytes) with status 413 and the message "El PDF pesa más de 20 MB", creating no plan and storing no file. When the declared body length exceeds the limit, it answers 413 before reading the body. When the declared length is missing or wrong, it stops reading once more than 20 MB has arrived and answers 413. Bodies at or below the limit behave as today. The browser treats any 413 by status code, whatever its body, as a rejection (REQ-22): the row is removed, the message shows as the danger alert under the dropzone and focus moves to the dropzone, including a 413 received during "Subiendo", which ends the upload. All other 4xx/5xx responses are failures (REQ-24).
  - Given a declared length of 20 MB plus 1 byte, then the response is 413 before the body is read, no plan exists and no file is stored; given exactly 20 MB and a valid PDF, then it is processed as today; given no declared length and a stream that errors if more than 20 MiB + 64 KiB (21,037,056 bytes) is read, then the response is 413 and the stream was not read to its end.
  - Given the server answers 413 with an empty or HTML body, also during "Subiendo", then the row is removed, "El PDF pesa más de 20 MB" shows as an alert and the dropzone is focused; given a 500, then the failed row with "Reintentar" shows.

## Edge cases and errors

- Upload or processing fails: inline failure with retry (REQ-24); nothing is saved and the active plan is not archived by a failed attempt that created no draft.
- Unsaved Datos edits: discarded by the ✕ on a processed row; kept when jumping between steps or when confirmation fails; the X does not ask (REQ-4, REQ-15, REQ-17).

## Non-functional requirements

- Heading text and the `.upload-wizard-modal` class are unchanged; new UI copy is Spanish (Mexico).
- Stepper, cards and dropzone are operable by keyboard alone. No new dependency (the uiarc dropzone is adapted in source, not installed); network calls are the existing upload call (plus the 413 check) and the existing plan-deletion call used by the ✕.

- "Datos" keeps the kcal and macro fields shown today; "Anterior" returns one step and shares state with stepper navigation.
- (v1.3) 20 MB means 20 MiB (20,971,520 bytes); upload and processing failures share one message format; the "review note" on the "PDF procesado" card is the one shown today. (v1.3.1, assumed) The draft-removal alert closes on the next attempt.
