## Overview

The assistant is rule-based keyword matching (no AI). It knows four topics (meal times, cart, recipes, plan), matches words only exactly or by stem, splits answers by scope, and never reads the daily logs. So "¿cuánto peso?", "¿qué puedo cenar?" and "¿cuánta agua tomé esta semana?" fail, and one typo gets the unknown reply. The data for all of these already exists: daily logs, goals, plan meals, options, complements, and the user and plan names. This feature makes matching tolerant and removes scopes, so every question searches everything. It adds meal detail, plus date-based weight, exercise, water and meal answers that use the dashboard's numbers. It handles small talk and ambiguity the way a chat should, and it redesigns the conversation layout. There is no schema change and no migration.

## Scope and dependencies

- **Also delivers chat-polish REQ-23** (server failures → HTTP 500 with a generic body and a logged error; 400 only for invalid input) as a task of this branch; **delivered** here (route tests in the coverage table). chat-polish stays `partial` until this branch merges. Its test-only failure injection is guarded like the date pin (REQ-13).
- **chat-polish strings still apply:** the implementation keeps the chat-polish copy listed under Copy ("Implementation strings").
- No new dependency is added: dish and recipe-name matching is in-house, built on the REQ-2 word matcher; the typing effect is in-project code adapted from prompt-kit's response-stream pattern, attributed in the repository's `THIRD_PARTY_NOTICES` file.

## Goals / Non-goals

- Goal: questions are understood despite accents, plurals, synonyms and small typos, and every answer covers all of the user's data (US1).
- Goal: "¿Qué puedo cenar?" leads, through buttons, to the full detail of a dish (US2). Weight, exercise, water and meal questions get correct, dated answers that match the dashboard (US3).
- Goal: the chat never dead-ends; whenever it is unsure, it asks back with closed-answer buttons (US4).
- Non-goal: conversation memory, MCP, external AI or LLM calls, writing data from the chat, and changing what the dashboard displays.

## Decisions

- **New spec plus a small amendment to assistant-chat-polish:** the old spec is large and already implemented.
- **No MCP and no real AI:** MCP adds nothing substantial now, and the project makes no external AI calls.
- **Stateless answers (no history in the request):** memory ("¿y la cena?") is a future feature; every button sends a self-contained message.
- **Story order US1 → US6:** US1 is already the largest phase, so the UI redesign goes last.
- **Typo allowance from the vocabulary word's length (≤4: exact; 5–7: 1 edit; ≥8: 2 edits; a transposition counts as 1 edit):** keeps "ahora" ≠ "hora", "pero" ≠ "peso" and "carritito" unknown, so existing tests stay valid. Computed in-house.
- **Dish and recipe-name matching is in-house, built on the REQ-2 word matcher; the feature adds no dependency (user decision 2026-10-29):** it reuses the accent, plural and first-letter rules the rest of the chat already follows (spike numbers: change log 1.7).
- **Dish match: symmetric word match, ranked by recall, then precision, then list order. A dish opens only when every non-stop word of the phrase matched (recall = 1) and the best candidate is exact or clearly ahead of the next, i.e. the next is strictly worse on recall, then precision (REQ-3):** sibling names exist ("Pollo asado" and "Pollo asado con verduras"), and a partial match must not open the wrong dish ("pizza con atún" would open "Sándwich de atún"). A candidate with a missing word is offered as "¿Quisiste decir…?" (alone or with others, up to 3), never opened. Word order and extra words in the name are tolerated. Conservative default; approved by the user 2026-10-29.
- **A phrase that is empty, under 3 characters, or made only of topic, slot or date words is not a dish name: REQ-6 step 4 falls through to the remaining steps ("¿Qué lleva la cena?" lists cena options, "¿Qué lleva el agua?" reads as Water), and only when nothing else resolves does the REQ-26 not-found reply apply; a unique word that covers the whole phrase and names one recipe ("lima" → "Sopa de lima") is found, on purpose; a typo in the first letter ("orno" for "horno") is not matched, accepted:** keeps "agua", "peso" or "cena" from opening a dish, and keeps the first-letter rule of REQ-2 (user decision 2026-10-29).

## Terms

- **Normalized text:** lowercase, accents removed (ñ compares as n), every non-letter, non-digit character treated as a space. A **word** is a run of letters and digits in it.
- **Edit:** one insertion, deletion or substitution of a letter, or a swap of two adjacent letters.
- **Never-fuzzy words:** ahora, ahorita, pasar, paso, pero, objeto, cuánto, cuánta, cuántos, cuántas. They match only exactly (so "cuánto" never matches "cuándo").
- **Slot:** a meal type of the active plan (name, time window, plan order). **Slot words:** desayuno, comida, cena, colación, almuerzo, merienda, snack, desayunar, comer, cenar. **Ordinal words:** the ordinals of a slot ref below in both genders and, normalized, with or without accents: primera/primer/primero, segunda/segundo, tercera/tercer/tercero, cuarta/cuarto, quinta/quinto, sexta/sexto, séptima/séptimo, octava/octavo, novena/noveno, décima/décimo. **Slot ref:** the slot name, or with duplicate names its ordinal form: Primera, Segunda, Tercera, Cuarta, Quinta, Sexta, Séptima, Octava, Novena, Décima + slot ("Segunda colación"); masculine slots (desayuno, almuerzo, snack) use Primer, Segundo, Tercer, Cuarto, Quinto, Sexto, Séptimo, Octavo, Noveno, Décimo. Beyond 10: "<Slot> <n>" ("Colación 11").
- **Slot button:** label "<Slot ref>" (plus " (<time>)" for duplicates that have a time); it sends "¿A qué hora es mi <slot ref>?" when the question was about times, otherwise "¿Cuál es mi <slot ref>?".
- **Generic name:** a recipe name that, normalized, is only a slot word or slot name followed by "opcion" and a number (e.g. "Comida opcion 1").
- **Preparation:** the recipe description, unless empty or starting with "Extraído de". **Steps:** the preparation split into sentences exactly as the recipe page splits it.
- **Complements:** the slot's shared add-ons with their amounts (e.g. "Agua natural · 1 vaso").
- **Today:** the server's date in America/Mexico_City. **Week:** Monday to Sunday containing today.
- **Water goal:** glasses = the active plan's minimum water liters (default 2 L, also with no plan or a plan with zero meal slots) ÷ 0.25, clamped to 4–12; the liters shown are the plan's liters, unclamped. **Exercise goal:** the user's goal, default 4 days a week; it always exists.
- **No active plan:** no active plan, or an active plan with zero meal slots (every REQ that says "no active plan"). The no-plan reply is the REQ-27 reply; Goals and Weekly add a no-plan line instead.
- **Date cues:** hoy, ayer, antier, anteayer, weekday names, month names, desde, hace, pasado/pasada, últimos/últimas are always cues. **Period nouns** (día(s), semana(s), mes(es), año(s)) are cues only inside a time-range construction: with hace, últimos/últimas, desde, pasado/pasada, esta/este, anterior, "en el" (only "en el mes", which means this month, REQ-14), or a number, weekday or month. Otherwise they are ignored as date cues ("Mi avance de la semana", "¿Cuántos días hice ejercicio?", "a la semana", "en la semana"). Words consumed by a phrase ("buenos días") are never cues. "desde" followed by a non-date word ("desde luego", "desde mi casa") is ignored and scanning continues (a bare "desde luego" stays unrecognized, because "desde" is an always-cue).
- **Question button:** sends its message as a visible user turn; its label may differ. **Navigation button:** a link, label followed by the lucide `ArrowUpRight` icon.
- **Recipe-list filter words (frozen from chat-polish v1.9 REQ-1):** stop words que, hay, en, mi, mis, de, del, el, la, los, las, con, para, por, tengo, cual, cuales, como, cuanto, es, un, una; also dropped: hora(s), horario(s), cuando, desayuno(s), comida(s), cena(s), colacion(es), carrito(s), plan(es), objetivo(s) and words starting with compr, receta, ingrediente, prepar, suplement, recomend.
- **REQ-3 stop words:** que, hay, en, mi, mis, de, del, el, la, los, las, con, para, por, tengo, cual, cuales, como, cuanto, es, un, una (the stop words of the frozen list above) plus **al, y, a**. A separate list from the frozen one: changing it never touches the Recipe-list filter. It is applied, after normalization, to dish phrases, recipe names (REQ-3) and the whole question (REQ-29); only these words are removed, topic words are not.

## User stories

### US1 (P1): Understand me, about everything
As the user, I want the assistant to understand how I actually type and to search all my data, so that I don't have to guess the right words or the right scope.

- **REQ-1:** Matching uses normalized text. Singular and plural forms match (s, es, z→ces). Each synonym group in Topics resolves to its topic.
  - Given "¿CUÁNTO PESÉ?", "báscula", "bascula", "¿Cuánto entrené?", "gym" or "¿Ya tomé agua?", then each resolves to weight, weight, weight, exercise, exercise, water.
- **REQ-2:** A word matches an entry exactly, by stem (* entries: exact prefix only), or fuzzily. Fuzzy: within the entry-length allowance (Decisions), counted against the entry's singular and plural forms, **and** the first letter matches. A word that exactly equals any entry, or is a never-fuzzy word, never fuzzy-matches. Multi-word entries ("buenos días", "cómo me llamo") match as whole phrases: consecutive words, each compared under these rules with its own length's allowance.
  - Matcher table (unit or e2e; NFR Testability): carito→carrito ✓; carrtio→carrito ✓ (swap); recta→receta ✓; desayno→desayuno ✓; ejersisio→ejercicio ✓ (2 edits, 9 letters); horarios→horario ✓; ahora, ahorita→hora ✗; pero→peso ✗; carritito→carrito ✗ (2 edits, 7 letters); pasar→pesar ✗ (never-fuzzy); lleva→llevo ✗ (both entries); garrito→carrito ✗ (first letter); vasto→vaso ✗ (4 letters); objeto→objetivo ✗ (never-fuzzy); cuanto→cuando ✗ (never-fuzzy).
  - Given "¿Qué hago ahora?", then no topic matches and the no-match reply shows (REQ-29).
- **REQ-3:** A dish phrase (the words after a dish cue, minus the cue and the REQ-3 stop words, Terms) is matched against the user's non-deleted recipe names by an in-house matcher built on the REQ-2 word matcher (no new dependency). Generic names are never candidates.
  - **Word match:** a phrase word matches a name word when the REQ-2 matcher accepts it in either direction (the phrase word against the name word as the entry, or the name word against the phrase word as the entry), so the typo allowance may come from either word; the first letter must match. Name words drop the same stop words. Word order and extra words in the name are tolerated. REQ-2's "never fuzzy if it exactly equals an entry" applies per name: a phrase word that exactly equals a word of one recipe name matches only that word, and never fuzzy-matches another word of that same name; it never blocks fuzzy matches against other recipes' names.
  - **Ranking:** a name's **recall** is the share of the phrase's non-stop words that match one of its words; its **precision** is the share of its words matched by a phrase word. Candidates are the names with recall above 0, ordered by recall, then precision (both high first), then the order the recipes were added.
  - **Outcome, first rule that applies:** (1) **exact:** the name equals the phrase, both normalized and with the REQ-3 stop words removed on both sides ("sandwich de atun" equals "Sándwich de atún"; "pollo asado con verduras" equals its name) → found (the detail). (2) The first candidate has **recall = 1** (every non-stop word of the phrase matched) and is **clearly ahead** of the second: there is no second candidate, or the second is strictly worse on (recall, then precision), i.e. it has a lower recall, or an equal recall and a lower precision → found. ## Non-functional requirements

- Dependencies: none added (dish matching is in-house; see Scope). No schema change and no migration.
- Performance: each answer within 1 s server time on the real dataset (32 recipes, 69 meals, 1 year of logs) on the dev machine. Split, because machine and data variance make a hard automated 1 s bound flaky: the automated check runs on a synthetic dataset of that volume, asserts ≤5 s per answer and logs the timings; the ≤1 s bound on the real data is verified manually by the user before the branch merges and noted in the batch report (still pending, the user's).
- Motion: typing ≤800 ms (min(800 ms, 18 ms × graphemes); exempt from chat-polish's 200 ms cap), fades ≤160 ms, nothing animated under `prefers-reduced-motion`. chat-polish AA contrast and 44×44 px touch minimums apply, extended by REQ-32 and REQ-35.
- Testability (Constitution 1): every REQ has a test that fails before and passes after, and every REQ keeps an e2e test written with its task. Required: the REQ-2 and REQ-3 tables, chat/dashboard parity, the REQ-14 table with a fixed today, empty states, multi-topic, paging, reduced motion, and chat-polish REQ-23. The scope tests are removed or rewritten. No REQ counts as covered by the test-only `resolved` field alone (contract); every REQ's test asserts the visible answer text or buttons. The REQ-3 table runs on its seeded fixture, never on the user's recipes.
  - Logic REQs: the fail-first proof is a unit test (`tests/unit/`, `npm run test:unit`, in-memory data, no database, server or browser). Checks that need no browser, including the REQ-2 and REQ-3 tables and the REQ-14 table, may be unit tests that call the same answer path as `ask()` with today supplied directly instead of the REQ-13 pin; they assert the answer text and buttons. The REQ requirements themselves are unchanged.
  - REQ-16 chat-vs-dashboard parity needs the dashboard's rendered tiles, so it stays an e2e test.
  - UI-only behavior (visuals, focus, typing effect, navigation closing the sheet): the proof is the e2e test, shown passing in the final full-suite run; its fail-first proof is a test-only breakage demonstration done in the stabilization step.
  - Cadence: each batch ends with `npx tsc --noEmit` and `npm run test:unit`; the full e2e suite runs once after the last development batch (stabilization, up to 3 review rounds) and again only if that step needs fixes.
- Snapshots: the assistant-panel and dashboard-search-bar visual snapshots are refreshed once, at the end of the feature, only with the user's explicit yes.

## Out of scope

MCP; external AI; conversation memory; logging data from the chat; persisted history; server streaming; dashboard display changes; `src/server.js` (legacy dev only); the nutrition normalizers behind persisted recipe fingerprints and ingredient keys, and the dashboard's own normalizer (changing them would change stored hashes and duplicate recipes on PDF re-upload); moving the dashboard to the server date.

## Assumptions

- Water ranges cap each day at the current goal, and "days met" uses the current goal; averages divide by every day in the range. Today's count is shown uncapped (REQ-17).
- A network failure, the 15 s timeout, a 400 and any other non-500 non-2xx keep "No pude responder en este momento."; only HTTP 500 uses the new copy (chat-polish REQ-8, REQ-23).
- Short replies like "ok", "sí" or "adiós" get the no-match reply; acceptable.
- The dashboard uses the browser's local date and the chat the server date in America/Mexico_City; they agree while the browser is in that time zone. The dashboard is not moved to the server date (Out of scope).
- The dashboard cannot log days that have not arrived, so the shared weekly computation (REQ-16) takes an end day: the dashboard passes Sunday, the chat passes today. Since no future day has data, the results are identical and REQ-16 parity is unaffected.
